## Why it matters most

U3–U6 treated the n8n workflows as a fixed thing to read. This doc is about
where that thing *comes from*. Nobody clicked nodes into place in the n8n
editor — every node, every wire between nodes, every JSON file in
`config/n8n/production/` is the printed output of a Python script. That's
"workflows-as-code": the workflow is source code (Python) first, a build
artifact (JSON) second, and a live n8n draft only when you deliberately
deploy it. This is the same shape you'll use in Phase A/B for the Python
backend — write the thing once, generate/deploy it deterministically, and let
a test suite catch drift — except here the "compiled" output happens to be
n8n's own workflow format instead of, say, a database migration.

## Six new ideas

1. **One Python function (`build()`) is the single source of truth for a
   36-node monolith that is never deployed.**
   `build_production_workflow.py:build()` constructs the full, original
   32-node CDL workflow purely as Python data structures, then writes it to
   `config/n8n/production/cdl-intake-production.json`. `deploy_n8n_workflow.py`
   *can* push that file to n8n, but only behind an explicit
   `--legacy-monolith` flag — the file `main()` immediately explains why:
   the monolith is "retired," replaced by four smaller workflows. So why does
   `build()` still exist and still get tested
   ([test_production_workflow.py](../../../tests/test_production_workflow.py))?
   Because `build_modular_workflows.py` calls it and **slices its output**
   into the four real workflows — see idea 3. It's the shared blueprint, not
   a deployment target.
2. **Deterministic node IDs, not random ones.** `stable_id()`
   ([:27-28](../../../scripts/build_production_workflow.py#L27-L28)) hashes a
   label like `"node:Write Candidate"` through `uuid.uuid5` (a
   *deterministic* UUID — same input, same output, every run, on any
   machine) instead of `uuid.uuid4` (random). Re-run the generator tomorrow
   and every node keeps the same ID it had today. That matters because n8n's
   API diffs/updates workflows by node ID — random IDs would make every
   regeneration look like a full rewrite instead of "nothing changed" or "one
   node's code changed."
3. **The modular suite is a *subset*, not a rewrite, of the monolith.**
   `build_modular_workflows.py` defines four Python `set`s of node names —
   `ROUTING`, `INTAKE`, `BOOKING`, `POST_CALL`
   ([:27-48](../../../scripts/build_modular_workflows.py#L27-L48)) — and
   `subset()`
   ([:62-81](../../../scripts/build_modular_workflows.py#L62-L81)) copies
   only the nodes whose name is in that set, plus only the connections whose
   *both* ends survived the cut. Each of the four workflow files still traces
   back to the exact same node-building code in `build()`; splitting them up
   changed *packaging*, not the underlying logic. New nodes bridging the
   split (like `Prepare Booking Input`) get added by hand afterward in
   `build_intake()` etc.
4. **Splitting off Booking created a chicken-and-egg deploy problem, solved
   by deploy *order*.** Booking became a subworkflow, called via an
   `n8n-nodes-base.executeWorkflow` node with `waitForSubWorkflow: True`
   ([:123-150](../../../scripts/build_modular_workflows.py#L123-L150)) — but
   that node needs Booking's real n8n workflow ID, which doesn't exist until
   Booking has already been deployed once. `deploy_n8n_suite.py` solves it by
   building the suite **twice**: once with a placeholder ID just to deploy
   Booking first, then rebuilding Intake/Routing/Post-Call with the real ID
   the API just handed back
   ([:64-73](../../../scripts/deploy_n8n_suite.py#L64-L73)). `ORDER =
   ("booking", "routing", "intake", "post_call")`
   ([:24](../../../scripts/deploy_n8n_suite.py#L24)) is not arbitrary — it's
   the dependency order.
5. **The deploy script asserts its own safety property instead of just
   promising it in a docstring.** After every upsert, `main()` checks
   `if any(item["active"] for item in manifest.values()): raise
   RuntimeError(...)`
   ([:86-87](../../../scripts/deploy_n8n_suite.py#L86-L87)). The docstring
   says "this deployer never activates workflows" — but the code doesn't
   trust that claim either; it re-reads what the API actually returned and
   crashes loudly if a workflow somehow came back active. A comment can go
   stale; a check that runs every time can't.
6. **The test suite checks the *committed JSON on disk*, not the Python
   objects in memory.** `test_modular_workflows.py` reads
   `config/n8n/production/modular/*.json` straight off disk
   ([:17-23](../../../tests/test_modular_workflows.py#L17-L23)) — it never
   imports `build_modular_workflows` or calls `build_suite()`. That means a
   run of the test suite tells you whether the *files you'd actually deploy*
   are correct, and it will catch the case where someone hand-edited the
   JSON, or regenerated it and forgot to commit the new version, or the
   generator changed but nobody re-ran it.

## Walkthrough — builders (`build_production_workflow.py`)

| Function | What it does | The interesting part |
|---|---|---|
| `node` [:31-40](../../../scripts/build_production_workflow.py#L31-L40) | The base constructor every other builder wraps: name, n8n node type, parameters, position, plus a stable ID. | Every specialized builder (`webhook`, `code`, `zoho_request`, …) is a thin wrapper around this one, so the "shape of a node" only has to be right in one place. |
| `code` [:55-57](../../../scripts/build_production_workflow.py#L55-L57) | Builds a Code node, and by default **prepends the entire contents of `workflow-src/cdl_helpers.js`** (the file from U5) to whatever small adapter snippet you pass it. | This is how U5's business logic ends up physically duplicated into every single Code node's `jsCode` string in the deployed JSON — one source file, many copies at build time. Editing `cdl_helpers.js` and re-running the builder is the only correct way to change that logic everywhere at once; hand-editing one node's JSON would drift silently. |
| `zoho_request` / `google_request` [:60-102](../../../scripts/build_production_workflow.py#L60-L102) | Build an HTTP Request node pre-wired with the right credential type, a 10s timeout, and (Zoho only) `retryOnFail`/3 tries/1s backoff. | Every Zoho call in the whole system gets retries "for free" just by using this constructor instead of a raw HTTP node — a platform-quirk fix (Zoho's 1-hour tokens, occasional 401s) baked into the builder instead of repeated by hand at every call site. |
| `connect` [:145-149](../../../scripts/build_production_workflow.py#L145-L149) | Appends a `{node, type, index}` edge into `connections[source]["main"][output]`, growing the list of output branches as needed. | n8n's connection format is "list of output branches, each a list of edges" — this function exists purely so the rest of `build()` can say `connect(connections, "A", "B")` instead of hand-writing that nested structure every time. |
| `build` [:152-570](../../../scripts/build_production_workflow.py#L152-L570) | Wires ~32 nodes end to end using the helpers above: routing, intake, calendar booking, post-call. | You don't need to read all 400 lines — skim it as "a long sequence of `nodes += […]` and `connect(...)` calls" and spot-check two or three sections you're curious about. |

## Walkthrough — splitting and deploying

| Function | What it does | The interesting part |
|---|---|---|
| `subset` [build_modular_workflows.py:62-81](../../../scripts/build_modular_workflows.py#L62-L81) | Filters the monolith's nodes/connections down to a named set, and stamps `meta.managedBy` / `meta.component` onto the result. | The `meta` block is a paper trail baked into the JSON itself — open any deployed workflow in the n8n UI and it says which script generated it, so nobody mistakes it for hand-built. |
| `build_booking` [:84-113](../../../scripts/build_modular_workflows.py#L84-L113) | Turns the booking subset into a standalone subworkflow: adds an `executeWorkflowTrigger` entry node and a passthrough terminal node, and patches one line of `Validate Callback`'s JS (`$('Resolve Candidate Result')` → `$input.first().json`) because that upstream node no longer exists in *this* workflow. | That one-line patch is the tax for splitting a workflow: any Code node that referenced a node which got sliced into a different file has to be rewritten to read from its new input instead. Idea 6 in U-earlier terms — see the dangling-reference test below, which exists specifically to catch anyone who misses a patch like this. |
| `build_suite` / `write_suite` [:209-224](../../../scripts/build_modular_workflows.py#L209-L224) | `build_suite` calls `build_monolith()` once, then all four `build_*` slicers against the same source. `write_suite` writes each to its file under `OUT_DIR` and prints node counts. | Re-running `python scripts/build_modular_workflows.py` regenerates all four files locally with **zero network calls** — the same "safe to run anytime" property `export_config.py` had in U6, just for generation instead of export. |
| `upsert` [deploy_n8n_suite.py:34-38](../../../scripts/deploy_n8n_suite.py#L34-L38) | POST if the workflow name isn't already live, PUT (to its existing ID) if it is. | Matching by *name*, not by ID, is what makes this deploy script idempotent across environments — you never have to know or track an ID by hand before the first deploy. |
| `main` [:41-87](../../../scripts/deploy_n8n_suite.py#L41-L87) | Dry-run by default (prints create/update + node counts per workflow and exits); `--apply` actually deploys, in dependency order, writes `deployment-manifest.json`, and asserts nothing came back active. | Same "dry-run is the default" discipline as U6's `deploy_vapi_tool.py` — consistent house style across every script that can touch a live system, from a different person's code, months apart. |

## Walkthrough — the test suite's techniques

| Test | What it actually checks | Why this technique |
|---|---|---|
| `test_every_emitted_code_node_has_valid_javascript_syntax` [test_modular_workflows.py:100-111](../../../tests/test_modular_workflows.py#L100-L111) | Shells out to `node -e "new Function(...)"` for every Code node's `jsCode` string. | Python has no JavaScript parser. Rather than skip syntax-checking the JS entirely, the test recruits the one interpreter on the machine that *can* check it — `node` itself — as a subprocess. `new Function(src)` parses `src` as a function body without running it. |
| `test_code_node_references_exist_in_each_workflow` [:157-165](../../../tests/test_modular_workflows.py#L157-L165) | Regex-scans every Code node's `jsCode` for n8n's `$('NodeName')` syntax and asserts each referenced name still exists *inside that same workflow file*. | This is the automated version of the manual patch in `build_booking` above — it exists because splitting a monolith into files is exactly the kind of change where "reference a node that used to be here" is an easy, silent mistake. It won't catch every bug (a typo'd name that happens to not match anything just silently fails at runtime in n8n instead), but it catches the class of bug the split itself introduces. |
| `test_suite_contains_no_forbidden_dependencies_or_secrets` [:167-170](../../../tests/test_modular_workflows.py#L167-L170) | Serializes all four workflows to one lowercase string, asserts words like `airtable`, `openai`, `client_secret`, `refresh_token` never appear. | Same "recurse the whole tree, don't trust a fixed field list" spirit as `redact()` in U6 — but here it's a *test assertion* (fail the build) instead of a *runtime transform* (redact and continue). Same idea, opposite job: one hides secrets on the way out, this one refuses to let them in in the first place. |
| `test_injects_booking_workflow_id_into_intake` [test_deploy_n8n_suite.py:7-18](../../../tests/test_deploy_n8n_suite.py#L7-L18) | Calls `inject_booking_id()` directly on a two-line fake `intake` dict, no file I/O, no network. | This is the one test in the whole file that imports and calls a *deploy*-script function directly instead of reading JSON off disk — and it can, safely, because `inject_booking_id` is pure data transformation with no side effect. Contrast with `deploy_n8n_suite.main()` itself, which is *not* unit-tested here at all — it can only be verified by an actual (careful, `--apply`-gated) deploy, which is exactly what the project `CLAUDE.md` means by "a change is only done when a real test call has been placed." |

## Try it yourself — predict, then trace

1. If you added a fifth node name to the `POST_CALL` set in
   `build_modular_workflows.py` that doesn't exist anywhere in `build()`'s
   output, what would `subset()` silently do — error, or produce a workflow
   missing that node? Trace the list comprehension at
   [:63](../../../scripts/build_modular_workflows.py#L63) to check.
2. Suppose you edit `workflow-src/cdl_helpers.js` (say, fix a bug in
   `resolveExperience`) but forget to re-run
   `python scripts/build_modular_workflows.py`. What state is the repo in —
   does anything fail, or does it look clean until someone diffs the
   generated JSON against a fresh regeneration?
3. `test_every_emitted_code_node_has_valid_javascript_syntax` runs `node -e`
   as a subprocess for *every* Code node in *every* workflow. Roughly how
   many subprocess calls does one test run make across all four files? (Count
   Code-type nodes across the JSON files, or just estimate from the node
   counts printed by `write_suite`.) What would happen to this test if
   Node.js weren't installed on the machine running it?
4. `deploy_n8n_suite.py`'s `main()` calls `build_suite()` a second time with
   the real booking ID, then calls `write_suite()` again
   ([:69-70](../../../scripts/deploy_n8n_suite.py#L69-L70)) — meaning
   `--apply` doesn't just deploy, it also overwrites the local JSON files a
   second time. If the deploy fails partway through (say, the Intake PUT
   errors after Booking already succeeded), what's left on disk, and does it
   match what's actually live in n8n at that point?

## Break it & fix it

1. **`build_booking`'s patch is a string `.replace()` on generated JS**
   ([:104-108](../../../scripts/build_modular_workflows.py#L104-L108)):
   `item["parameters"]["jsCode"].replace("const intake =
   $('Resolve Candidate Result').first().json;", "const intake =
   $input.first().json;")`. What happens — silently or loudly — if someone
   edits the corresponding line inside `cdl_helpers.js`'s adapter code in
   `build()` so the original string no longer matches exactly (extra
   whitespace, renamed variable)? Would any existing test catch that? (Hint:
   `.replace()` on a string that doesn't match just... does nothing.)
2. **Trace the dangling-reference test's blind spot.** It only checks
   `$('NodeName')` — n8n's *cross-node* reference syntax. `Prepare Booking
   Input` in `build_intake()` also reads `$json.data` — a reference to *this
   node's own input*, not another node. If a rename inside `subset()`'s node
   set broke a same-node `$json.*` field reference instead of a cross-node
   `$('...')` one, would `test_code_node_references_exist_in_each_workflow`
   notice? What kind of test *would* catch that class of bug?

## Review questions

**Q: Why generate n8n workflows from Python instead of building them by hand
in the n8n editor?**
A: Three reasons, in order of how much they'd matter to a hiring manager:
code review (a workflow diff is a Python diff, reviewable in a PR, instead of
"trust me, I clicked the right things"), determinism (the same script run
twice produces the same node IDs and structure, so redeploys are safe and
diffable), and reuse (the same builder functions — `zoho_request`, `code` —
guarantee every Zoho call gets retries and every Code node gets the shared
business-logic file, without anyone having to remember to configure that by
hand on node #14).

**Q: The monolith workflow (`cdl-intake-production.json`) is retired and
never deployed — so why does the codebase still build it and test it?**
A: Because it's not dead code, it's the shared source. `build_modular_workflows.py`
doesn't reimplement the four production workflows from scratch — it calls the
same `build()` function that produces the monolith, then slices its output by
node name into four files. Retiring the monolith *as a deployment target*
and retiring it *as a Python function* are two different things; only the
first happened.

**Q: Why does the deploy script build the workflow suite twice
(`build_suite()` called with a placeholder ID, then again with the real
one)?**
A: Because Booking became a subworkflow that Intake calls by ID, but that ID
doesn't exist until Booking has been deployed at least once — a genuine
chicken-and-egg problem. The fix is deploy order plus a second build pass:
deploy Booking first with a placeholder value in the file, read back the real
ID the API returns, then rebuild (and redeploy) the other three workflows
with that real ID wired in.

**Q: The test suite reads the committed JSON files on disk instead of
calling the Python builder functions directly. What does that catch that a
test against the builder functions wouldn't?**
A: Drift between the generator and what's actually checked in — someone
hand-edits the JSON directly, or changes the builder but forgets to
regenerate and commit, or regenerates locally but the committed file is
stale relative to `cdl_helpers.js`. Testing the artifact you'd actually
deploy, not the code that (in theory) produces it, is the same principle as
"verify persisted state, not the script that's supposed to write it" from the
project's own verification rules.
