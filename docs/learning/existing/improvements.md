# Weaknesses found while reading the existing system

A running list, added to during Phase U. Each item: what, where, impact, and
which planned step fixes it. This becomes the "why I built the Python API"
section of `../build-notes.md`.

Status: **observed** = seen in the config/code, **confirmed** = reproduced.

| # | Weakness | Where | Impact | Fixed by |
|---|---|---|---|---|
| W1 | No durable store of lead details outside Zoho. If Zoho fails during intake the caller hears "a recruiter will follow up", but the details live only in VAPI's call log. Successful n8n executions aren't saved (`saveDataSuccessExecution: none`). | 02 Intake → *Respond Candidate Failure* | Lead lost during a CRM outage | Steps 5 and 8 (Postgres + outbox) |
| W2 | Post-call replies 200 *before* writing Zoho, so VAPI never retries. If Zoho is down, the transcript and summary are lost. | 04 → *Acknowledge Post Call* | Transcript lost | Step 5 (commit, then 200) plus Step 8 |
| W3 | A new caller who hangs up before the tool call produces nothing. Post-call finds no Candidate, and the IF false branch is unconnected. | 04 → *Candidate Found?* | Partial lead lost, even though the structured data was available | Steps 5–6 (store the partial lead as `needs_review`) |
| W4 | Placeholder phone `+10000000000` is used to avoid an empty-search error. | 01 and 04 search URLs | Hides a missing phone and makes a pointless API call | Step 6 (explicit missing-field handling) |
| W5 | Dedupe is search-then-create. Two calls from the same phone at once can both see "not found" and both create a record. There's no uniqueness enforced in Zoho (AUDIT #13 is still open). | 02 → *Find Candidate* → *Write Candidate* | Duplicate candidates | Step 5 (`UNIQUE(phone_e164)` in Postgres plus upsert) |
| W6 | **Confirmed (U3), with a correction to the original prediction.** *Prepare Booking Input* throws if the intake Note fails (no `onError`, proven both by local Node execution and by reproducing it live on a duplicate workflow with pinned mock data). The throw is real and no Respond node ever runs after it — but the predicted HTTP reply was wrong: against `webhook-test` (`executionMode: "test"`) it was **200 OK with the raw trigger request echoed back**, not the expected 500 with no `results`. Either way, **no `results` array is ever returned**, so VAPI still can't get a valid tool-call answer — the core danger holds even though the exact wire response doesn't match the prediction. **Still open:** whether the *production* webhook URL (`webhook/...`, not `webhook-test/...`) behaves the same way — n8n has open GitHub issues about response-mode inconsistency between test and production webhooks, so this needs a separate check before assuming it generalizes. | 02 → *Prepare Booking Input* | Caller may hear a tool error (or dead air, depending on how VAPI parses a 200 with no `results`) even though the Candidate *was* saved, and the calendar is never booked | **Decided 2026-09-24**: make the failed note non-fatal (not `onError` + route-to-Respond). Reasoning: the candidate is already saved by this point, so stopping the booking flow over a note failure is disproportionate — the note is a nice-to-have record, not a precondition for booking. Implementation note: don't let this go silent — carry a `noteSaved: false` flag forward so the failure is still visible downstream (ties into Step 10 observability), rather than just deleting the throw. Verify production-URL response behavior separately (still open). |
| W7 | Nodes reference each other by name (`$('Normalize Route Request')`), so renaming one breaks others silently until runtime. | all workflows | Fragile edits | Mitigated: workflows are generated from `scripts/build_modular_workflows.py` and tested |
| W8 | The Zoho access token isn't explicitly cached (AUDIT #22). The n8n OAuth credential handles refresh itself, so check this in U6/U7. | credentials | Possible rate-limit pressure | Step 7 (token cached for 1 h) |
| W9 | *(observed, U3)* Retry budget is longer than VAPI's wait. Each Zoho node: 3 tries × 10 s timeout + 2 × 1 s = 32 s worst case, and intake makes 3 Zoho calls before replying. VAPI's `timeoutSeconds` is 30. | 02 HTTP nodes vs `config/vapi/tool.logApplicantInfo.json` | When Zoho is *slow* (not down) VAPI gives up while n8n keeps working; the write may still land | Step 8 (durable write, short timeouts) |
| W10 | *(observed, U3)* A failed Zoho search is treated as "not found". *Build Candidate Write Request* sees no `data`, picks `POST`. | 02 → nodes 5 and 6 | A brief search failure can create a duplicate candidate | Step 5 (`UNIQUE(phone_e164)` plus upsert) |
| W11 | *(observed, U3)* Two guard nodes with the same job disagree on what counts as failure. *Prepare Booking Input*: `record?.code !== 'SUCCESS'` throws even when `record` is missing entirely (strict — added per `2026-08-12_1456_codex-cdl-handoff.md` after a real bug where the Note API response leaked into Calendar Booking's input). *Verify Booking Note*: `record?.code && record.code !== 'SUCCESS'` only throws when `code` is present and wrong, so a missing `record` is silently treated as OK (lenient). No design note explains the second, looser check; git shows both nodes landed in one untracked-work snapshot commit (`392abe9`), so no per-node history survives either. | 02 → *Prepare Booking Input* (14) vs *Verify Booking Note* (17) | Unclear whether node 17's leniency is deliberate (its throw is post-reply and harmless either way, per W6's analysis) or an inconsistency that would bite if the same guard pattern is reused pre-reply elsewhere | Decide during U3 review: document the intended rule for this guard pattern once, then make both nodes follow it |
